# План отдельной поставки плагинов

## Что уже есть в KeyDeck

- `keydeck/plugin_api.py` задаёт `PluginBase`, `Action` и `PluginContext`.
- `keydeck/plugin_manager.py` обнаруживает, загружает, отключает и выгружает плагины.
- Настройки и кэш плагина уже хранятся отдельно от его кода в `%LOCALAPPDATA%\KeyDeck\plugins\<id>\`.
- Страница **Plugins** в настройках показывает найденные плагины и позволяет их отключать.
- Сейчас релизная сборка всё ещё включает каталог `plugins` в EXE. Каталога удалённых пакетов, установки из интерфейса и отдельных релизов плагинов пока нет.

Поэтому не нужно заново проектировать Plugin API или повторно реализовывать управление включением. Основные задачи — разделить код плагинов и Core, договориться о формате каталога/пакетов и добавить безопасную установку.

## Этапы по версиям

### KeyDeck 0.3.x — разделение каталогов и переход

- Сохранить обратную совместимость с существующими `manifest.json`, назначениями кнопок, настройками и кэшем.
- Считать исходный `plugins/` каталогом разработки, а `%LOCALAPPDATA%\KeyDeck\installed_plugins\` — каталогом отдельно установленных плагинов.
- При конфликте ID в режиме разработки приоритет у исходника; каталог с установленными плагинами становится самостоятельным источником для сборки.
- Добавить в манифест обязательные для публикации поля `version`, `min_keydeck_version` и точку входа; проверить их до загрузки.
- Выпустить переходную версию, которая переносит код из старой встроенной поставки в каталог установленных плагинов. Только после этого удалять плагины из EXE: прежние версии хранят код внутри временной распаковки EXE, а не рядом с ним.

### KeyDeck 0.4.x — библиотека и независимые релизы плагинов

- Добавить каталог плагинов в интерфейс **Plugins**: поиск, описание, версия, совместимость и состояние установки.
- Утвердить схему каталога с ID, автором, описанием, поддерживаемыми версиями Core и ссылкой на релиз.
- Публиковать каждый плагин отдельным архивом и отдельным GitHub Release/tag, например `plugin-MultiTool-v1.2.0`; изменение плагина не должно требовать выпуска новой версии Core.
- В EXE оставить только Core и метаданные/клиент библиотеки; код плагинов загружать по запросу пользователя.
- Установку, обновление и удаление выполнять через интерфейс; не удалять настройки и кэш вместе с кодом.

### KeyDeck 0.5.x — проверка пакетов и независимые обновления

- Ограничить загрузки официальным источником, размер архива и структуру содержимого.
- Сверять SHA-256 по опубликованной сумме и безопасно распаковывать во временный каталог; отклонять выход путей за каталог плагина, дублирующие пути и ссылки.
- Проверять ID, версию, совместимость и файлы манифеста до атомарной установки.
- Обновлять плагины отдельно от Core; сохранять предыдущую версию до успешного запуска и предоставлять откат.
- Ошибки сети, проверки и установки показывать пользователю, не меняя активную версию при неудаче.

### KeyDeck 0.6.x — разрешения и данные

- Описать запрашиваемые возможности плагина в манифесте и показывать их до установки/включения.
- Секреты и настройки хранить в пользовательском каталоге данных, не в каталоге кода и не в архиве плагина.
- Не считать Python-плагин изолированным или безопасным только из-за Plugin API: полноценная песочница потребует отдельного процесса и IPC. До её появления интерфейс должен честно предупреждать, что установленный Python-код исполняется с правами пользователя.

## Выполнено в текущем изменении

- Core может обнаруживать и загружать плагины из нескольких каталогов.
- Добавлен отдельный путь `%LOCALAPPDATA%\KeyDeck\installed_plugins\` для кода, устанавливаемого библиотекой.
- Сохранены существующий каталог исходников и API конструктора `PluginManager`; source-каталог имеет приоритет при конфликте ID.
- Проверки покрывают обнаружение/загрузку из отдельного каталога и разрешение конфликта.

Текущий EXE всё ещё содержит плагины. Удалять их из сборки до переходного переноса и интерфейса загрузки нельзя: иначе существующие назначения останутся без исполняемого кода.
